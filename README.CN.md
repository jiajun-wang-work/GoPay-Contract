## 1. 产品目标

GoPay 是构建在 Midnight 上的多资产隐私兑换 DApp，支持不同法币稳定币与主流加密资产之间的兑换，并保护用户在应用内部的余额、兑换数量、收款信息及资金流转关系。

推荐第一版采用 **shielded 资产 + RFQ 做市商报价 + Midnight 原子结算**，优先复用原生 shielded token 的消费与守恒机制；自定义私密余额凭证作为特定接入需求下的备选。做市商预先准备库存，用户确认净到账金额，合约验证双方授权并完成资金交换。后续再评估隐私 AMM。

GoPay 对每笔成功的用户 swap 收取 **0.5%（50 bps）平台手续费**，全部进入平台运营金库，作为 GoPay 运营费用保留。手续费由结算合约强制执行，所有交易对和调用入口适用，不依赖前端收费。

长期扩展目标是 **通用兑换核心 + 资产注册表 + 可扩展适配器 + 通用 shielded 发行逻辑**。新增兼容资产以注册和配置为主，不修改兑换核心；新链或特殊资产可能需要新增适配器。

本方案描述的是目标架构。原生 shielded token、合约托管、钱包交易组合、签名验证及失败回滚的具体能力，需要针对选定的 Midnight 网络、Compact 编译器和 SDK 版本验证。

## 2. 隐私目标与边界

### 2.1 对不同观察者的保护范围

| 信息 | 公开链观察者 | 相关服务或交易对手 |
|---|---|---|
| 交易存在、时间、合约地址、入口 | 仍然可见 | 可见 |
| GoPay 内部用户余额 | 目标为隐藏 | 用户持有自己的私密记录 |
| 兑换数量与收款输出 | 目标为隐藏 | 做市商通常知道自己的报价和成交条件 |
| 兑换币种 | 目标为尽量隐藏 | 报价提供者通常知道；公开访问模式可能泄露 |
| 外部链存入与提现 | 原链上可能公开 | 桥或托管方通常知道相关入出金信息 |
| IP、请求时序、服务日志 | 不由链上 ZK 自动保护 | RPC、报价服务或中继可能获得 |
| 证明的私密输入 | 不应公开上链 | 远程证明服务可能接触，取决于实际部署方式 |

GoPay 不承诺让交易在公开链上“消失”，也不承诺跨链前后不可关联。小规模匿名集合、独特金额和紧邻的存取时间，都可能降低实际隐私。

### 2.2 NIGHT 的特殊边界

官方资料将原生 NIGHT 定义为 unshielded 资产。不能直接将其当成原生隐私代币。

若支持 NIGHT 的内部私密流转，应通过真实 NIGHT 储备支撑 GoPay 私密余额凭证。存入、赎回及储备变化仍可能公开，不能将内部凭证宣传为协议原生 shielded NIGHT。

### 2.3 公开状态原则

- 用户地址、余额、订单明细不得直接写入公开余额表。
- 私密输入不得通过日志、返回值、公开状态更新或可识别的访问轨迹泄露。
- 私密数据进入 witness 只是起点；必须验证其约束，并审查最终公开交易数据。
- `disclose()` 不是加密。
- 不应认为移除 ledger 的 `export` 就能让链上数据保密。

## 3. 资产范围与身份

### 3.1 候选资产

| 类别 | 候选资产 | 接入要求 |
|---|---|---|
| 美元稳定币 | USDC、USDT | 确认来源链、发行版本、桥及兑付路径 |
| 欧元稳定币 | EURC、EURCV | 分别确认发行方、来源链、代币地址及兑付路径 |
| 英镑稳定币 | tGBP | 确认具体发行版本、来源链及赎回安排 |
| 瑞士法郎稳定币 | ZCHF | 确认资产机制、来源链及兑付方式 |
| 日元稳定币 | JPYSC、JPYC | 分别确认发行版本、代币地址及赎回安排 |
| 巴西雷亚尔稳定币 | BRLA | 确认发行方、来源链及兑付路径 |
| 新加坡元稳定币 | XSGD | 确认具体发行方、来源链和赎回路径 |
| 澳大利亚元稳定币 | AUDD | 确认发行方、来源链及赎回安排 |
| 尼日利亚奈拉稳定币 | cNGN | 确认发行方、来源链及兑付路径 |
| 加密资产 | BTC、ETH | 桥接、托管凭证或受支持的原生发行形式 |
| Midnight 资产 | NIGHT | 公开存取与有储备的私密内部凭证 |

计划接入范围为 9 种法币对应的 12 种稳定币；加密资产交易类别仅保留 BTC、ETH。NIGHT 继续作为 Midnight 原生资产单列。EURC 与 EURCV、JPYSC 与 JPYC 必须各自注册，不能因锚定同一种法币而合并为同一资产。代币符号保留原始大小写，例如 `tGBP` 和 `cNGN`。

此清单不代表这些资产已原生部署在 Midnight，也不代表存在可直接使用的生产级桥。其他国家的稳定币通过注册表扩展，不将国家或币种写死在兑换逻辑中。

### 3.2 资产唯一标识

概念定义：

```text
assetId = Hash(
  sourceChain,
  sourceTokenAddressOrNativeId,
  issuerOrBridgeAdapter,
  assetVersion
)
```

相同名称、不同来源或不同桥的 USDC 必须是不同资产。若允许互换，需另设有实际兑换支撑的路径，不能直接合并余额。

建议注册字段：

```text
AssetConfig {
  assetId
  sourceChain
  sourceTokenAddressOrNativeId
  issuerOrBridgeAdapter
  adapterId
  adapterVersion
  shieldedTokenId
  assetVersion
  decimals
  settlementRepresentation
  depositCap
  depositEnabled
  swapEnabled
  withdrawEnabled
  configVersion
}
```

`settlementRepresentation` 区分原生 shielded 资产、公开资产的内部凭证及桥接凭证。精度来自经过验证的具体资产配置，不能仅根据代币名称推断。

`adapterId` 与 `adapterVersion` 指定接入验证逻辑；`shieldedTokenId` 绑定实际使用的 Midnight shielded 资产。只采用内部 Note 的表示不能伪造一个原生 token 标识，应使用明确的表示类型和可选字段。原始资产身份、兑付来源和 shielded 标识的对应关系不能任意替换；变更这些关系应创建新资产版本并定义迁移流程。

### 3.3 外部资产的 shielded 表示

上述 12 种稳定币及 BTC、ETH 可以设计为有真实资产支撑的 shielded 表示，主要有两种路径：

| 路径 | 发行与兑付方式 | 前提 |
|---|---|---|
| 发行方原生发行 | 发行方在 Midnight 发行 shielded token 并承担赎回责任 | 发行方合作及实际部署；GoPay 不能自行宣称包装资产是官方发行 |
| 有储备的包装资产 | 原链锁定资产，Midnight 验证入账后铸造；赎回时销毁并释放储备 | 可靠的桥、托管或跨链验证机制 |

例如，锁定 USDC 后创建的 `gpUSDC` 是拟议包装资产名称，不代表已经存在的官方代币。协议原生资产类型不能仅靠切换标志变为 shielded，转换需要应用层的资产绑定逻辑。原链存入和提现仍可能公开，原链历史不会被隐藏。

## 4. 系统架构

```mermaid
flowchart LR
    A[外部链资产 / 原生 NIGHT] --> B[桥接或存取适配器]
    B --> C[Vault / Factory 资产验证与发行]
    C --> H[Midnight shielded 资产或备选内部凭证]
    H --> D[做市商 RFQ 报价]
    D --> E[PrivateSwap 验证与结算]
    E --> F[新的私密余额]
    F --> G[继续支付或兑换]
    F --> B
```

### 4.1 合约逻辑模块

| 模块 | 职责 | 约束 |
|---|---|---|
| AssetRegistry | 资产注册、精度、适配器、额度与操作开关 | 不允许任意替换旧资产兑付来源 |
| AdapterRegistry | 接入模块的身份、版本、验证权限与启停管理 | 仅批准的模块可验证对应资产；不能跨资产任意发行 |
| ShieldedAssetFactory | 复用发行模板，创建并绑定 shielded 资产标识 | 创建资产不等于已存在储备；铸造必须验证入账 |
| GoPayVault | 实际资产存取及储备绑定，按所选表示协调发行或凭证创建 | 实际入账与新增可花费余额必须绑定 |
| PrivateSwap | 报价、授权、手续费、有效期及资金交换 | 资金变化与成交状态必须原子完成 |
| PlatformTreasury | 接收并保管所有 swap 的平台手续费，供 GoPay 运营使用 | 与用户托管储备隔离，仅授权运营多签可支出 |
| Governance | 资产配置、金库管理、暂停、升级 | 多签、延迟生效、权限最小化；当前费率固定为 50 bps |

以上为逻辑模块，不要求全部独立部署。若采用内部 Note，第一版建议将 Vault 内部记账与兑换结算放在同一核心合约中。若采用原生 shielded token，应优先复用原生资金机制，并验证发行、钱包与兑换组合能力。Factory 可以实现为通用多资产发行模块，或复用同一模板部署独立发行合约，具体选择由能力验证决定。

### 4.2 链下组件

| 组件 | 职责 | 不应拥有的权限 |
|---|---|---|
| 钱包 / GoPay 客户端 | 保存私密记录、生成证明、授权交易、恢复余额 | 不向服务端发送用户花费密钥 |
| PriceProvider | 获取并传递可执行 RFQ 报价 | 不能替用户授权资金 |
| 做市商 | 提供报价及有效库存 | 不能更换用户已授权的输出 |
| PriceOracle（可选） | 提供参考价格或风险检查依据 | 不能替代双方授权和实际库存 |
| 中继服务 | 传递交易或提供费用协助 | 不能改写收款输出 |
| 桥接适配器 | 验证外部存款、处理兑付 | 不得凭普通 API 回应任意创建余额 |

第一版固定报价结算不必依赖预言机决定成交价。若后续使用预言机，应另外定义数据来源、签名、时间新鲜度、偏差阈值及异常停用机制。

### 4.3 无需修改兑换核心的扩展方式

`PrivateSwap` 仅处理资产 ID、资金证明、报价和授权，不编写 USDC、JPYC 等币种专用分支。敏感资产及数量通过私密输入与证明处理，概念接口不意味着公开传参。

通用核心验证资产当前可交易、输入有效、逐资产守恒、双方输出授权及报价条件。新增资产复用这些规则，但注册本身不提供储备或流动性。

| 新增场景 | 修改兑换核心 | 接入工作 |
|---|---|---|
| 已支持链上的兼容标准代币 | 通常不需要 | 验证代币行为，注册配置，复用适配器与发行逻辑 |
| 已有 Midnight shielded token | 通常不需要 | 注册真实标识，验证钱包及结算兼容性，无需重复包装 |
| 同币种的另一桥接版本 | 不需要 | 注册为独立资产，不能合并债权 |
| 新的区块链 | 通常不需要 | 开发、验证并批准新链适配器 |
| 转账扣税、余额自动变化等特殊代币 | 不应直接接入 | 专用处理或拒绝支持 |
| 底层协议或 SDK 不兼容升级 | 可能需要 | 兼容升级和回归验证 |

上述可扩展性以统一结算表示和适配器接口足够兼容为前提；固定电路规模、证明类型变化或不支持的协议能力仍可能要求升级。新增适配器是经批准的验证逻辑，不是假设 Compact 支持任意运行时插件加载。

### 4.4 通用发行与适配器接口

`ShieldedAssetFactory` 是 GoPay 拟议模块，不代表已有现成通用跨链产品。两种候选实现是：

1. 一个多资产发行合约，按资产配置管理发行权限。
2. 每种资产部署同一发行模板，隔离权限并复用代码。

新增部署不等于修改兑换核心。所有发行实例必须绑定资产身份和适配器验证范围，防止用 A 资产的入账证明铸造 B 资产。

概念流程：

```text
注册来源资产 → 绑定已批准适配器 → 创建或登记 shielded 标识
验证真实存款及最终性 → 防重放 → 铸造对应可花费资产
消费/销毁对应资产 → 创建唯一赎回请求 → 按跨链状态机兑付
```

适配器统一输出的已验证信息至少包括：

```text
DepositEvidence {
  sourceChain
  sourceToken
  actualReceivedAmount
  uniqueDepositId
  destinationNetwork
  destinationContract
  destinationAssetId
  recipientCommitment
  adapterVersion
}

RedemptionRequest {
  sourceAssetId
  amount
  destinationChain
  destinationAddress
  uniqueRedemptionId
}
```

所有字段必须绑定到可信证明或授权跨链消息；不能信任用户填写的到账金额。存款 ID 的域需覆盖来源链、交易和事件位置，且必须防止跨发行实例重复铸造。

转账扣税代币按实际收到的数量处理。余额自动变化的资产需要专门定义储备与债权份额关系，不能照搬固定数量 1:1 发行规则。不兼容资产默认拒绝接入。

### 4.5 新资产上线流程

1. 验证来源、精度、代币行为、最终性及兑付机制。
2. 选择兼容适配器；没有适配器时先开发和验证。
3. 注册新资产，创建或登记其 shielded 标识并核对绑定关系。
4. 以受限额度验证存入、隐私转账、兑换、赎回及故障恢复。
5. 做市商准备真实库存，并接入报价、钱包展示和索引服务。
6. 按治理流程启用相关操作，监测额度与兑付状态。

上线分别要求“可发行、可兑付、可兑换”。注册和发行不自动产生储备或市场流动性。核心目标是让兼容资产配置化接入，不是让任意资产未经验证自动获得可靠的 shielded 表示。

## 5. 私密余额模型

### 5.1 Note 结构

本节的自定义 Note 是内部凭证方案，只有明确需要该层时才实现。采用原生 shielded token 的资产应复用协议原生消费与守恒机制，不重复维护一份可同时花费的余额。后文涉及 Note 的接口与测试，在原生路径下对应实际 shielded 输入、输出及消费验证。

避免公开的 `balances[user][asset]`。对需要内部凭证的资产，采用 Note 模型：

```text
Note {
  assetId
  amount
  ownerKey
  uniqueNonce
}

commitment = Commit(
  protocolDomain,
  networkId,
  contractAddress,
  protocolVersion,
  Note;
  freshBlinding
)
```

以上为概念记法，不是 Compact 标准库的可直接调用签名。实现时需要确定规范化编码、字段范围和具体承诺原语。

### 5.2 链上状态

```text
noteCommitments     Note 承诺集合或历史 Merkle 树
spentNullifiers     已消费 Note 的不可重复标记
orderNullifiers     已成交或已取消订单的不可重复标记
assetConfigRoot     资产配置集合的承诺根
feeConfig           固定费率 50 bps、计费规则与版本
treasuryConfig      平台金库接收标识、权限与配置版本
pauseConfig         分操作的暂停状态
governanceConfig    管理权限及待生效配置
```

承诺、nullifier、根和交易结构可以公开；不应从这些数据直接恢复用户余额。树容量、历史根保留窗口、追加记录可用性和迁移方式都需要明确。

### 5.3 消费证明

消费一个 Note 时必须验证：

1. 根据私密内容重算的承诺等于 Merkle 路径中的叶子。
2. 路径对应协议允许的根。
3. 消费者拥有该 Note 的授权秘密。
4. Nullifier 根据所有者秘密和 Note 唯一身份确定性派生。
5. Nullifier 尚未使用。
6. 输出及找零满足逐资产守恒，收款人和金额符合授权。

Nullifier 与承诺必须使用不同的域。用户不能通过替换随机数生成另一个 nullifier 来重复花费同一张 Note。

### 5.4 储备与债权关系

Note 是对 GoPay 所接收资产的内部债权，不是仅凭一个承诺就创造的真实资产。

- `deposit` 必须验证实际资产到账与创建的 Note 一致。
- `withdraw` 必须将 Note 消费与相应兑付绑定。
- 跨链资产的可信度取决于桥、发行方或托管机制，ZK 不能证明未经验证的外部储备真实存在。
- 单个适配器出问题时，应能停止该资产新增风险；已有债权如何退出要提前定义。

若某资产可以直接采用 Midnight 原生 shielded token，应优先评估复用其原生消费和守恒机制。自定义 Note 层与原生资产之间的转换不能形成两份可同时花费的余额。

## 6. RFQ 兑换流程

### 6.1 报价结构

```text
Quote {
  networkId
  contractAddress
  protocolVersion
  inputAssetId
  outputAssetId
  inputAmount
  swapPrincipalAmount
  netOutputAmount
  feeAssetId
  feeAmount
  feePayer
  feeConfigVersion
  treasuryConfigVersion
  treasuryRecipientCommitment
  expiry
  quoteNonce
  userOrderCommitment
  authorizedOutputCommitments
}
```

报价必须绑定网络、合约和版本，防止跨网络、跨合约或升级后的重放。做市商签署报价，用户另外授权自己的输入和最终输出。具体签名方案与双方证明组合能力需验证后选择。

### 6.2 USDC 兑换 JPYC 示例

1. 用户已持有 GoPay 内部 USDC 私密余额。
2. 做市商已准备 JPYC 库存。
3. 用户通过私密连接向选定做市商请求报价。
4. 客户端显示输入数量、净到账数量、费用和过期时间。
5. 用户与做市商分别授权各自资金和指定输出。
6. `settleSwap` 校验报价、双方授权、输入有效性及资产守恒。
7. 同一次业务原子结算消费双方输入，生成双方输出、找零和费用输出，并标记订单已成交。
8. 用户收到可验证的加密收据及新 Note 信息。

做市商报价签名不等于库存已锁定。如果库存被其他订单使用，本次结算应失败，不能单边扣款。

### 6.3 状态与撤单

第一版采用整单成交，不支持部分成交。

```text
有效报价 / 授权
  ├── 成交：消费订单标记，资金一起交换
  ├── 撤单：消费与成交互斥的订单标记
  └── 过期：结算检查不再允许成交
```

撤单与成交竞争时，只能有一个成功。过期不必逐单写入链上状态，但必须依据链上可验证的有效期规则检查，不能信任客户端时间。

### 6.4 固定 0.5% 平台手续费

每笔成功的用户 swap 必须收取 0.5% 平台手续费，不设交易对、用户、做市商或直接合约调用的免手续费入口。费用全部归 GoPay 平台运营金库，不返还做市商，也不作为用户资产储备重复记账。

本版采用以下统一计费口径：**以用户输入总额为基数，使用输入资产收费，并从输入总额中扣除。** 用户无需另外准备第三种代币。

```text
feeBps = 50
bpsDenominator = 10_000
inputAmount = 用户确认的输入总额（不含钱包找零）
feeAmount = ceil(inputAmount × 50 / 10_000)
swapPrincipalAmount = inputAmount - feeAmount
feeAssetId = inputAssetId
feePayer = 发起 swap 的用户
```

金额按资产最小单位计算，手续费向上取整，避免小额订单四舍五入为零。实际费用最多比数学上的 0.5% 多不足一个最小单位；前端必须显示实际费用。若兑换本金或最终净到账为零则拒绝成交。实现需使用有范围约束的安全整数运算，不能让中间乘积溢出。

做市商针对 `swapPrincipalAmount` 提供报价，`netOutputAmount` 是用户最终实际到账数量；输出侧不再重复扣取这笔平台费。报价点差、外部桥接费用和网络资源消耗应分别披露，不能混入平台 0.5% 的计算或宣传为平台费。

示例：用户输入 1,000 USDC，平台收取 5 USDC，剩余 995 USDC 用于兑换。假设做市商报价为每 USDC 兑换 150 JPYC，则用户收到 149,250 JPYC，平台金库收到 5 USDC。此汇率仅用于演示，不代表实时价格。

| 项目 | 规则 |
|---|---|
| 适用范围 | 所有成功的用户 swap，包括稳定币、BTC/ETH 及支持的 NIGHT 交易对 |
| 收费资产 | 用户输入资产的相同资产 ID 和表示，不能按符号替换为另一桥接版本 |
| 收款方 | 当前有效配置指定的平台运营金库 |
| 失败、过期或撤单 | 不收取平台 swap 手续费；网络资源仍可能消耗 |
| 存入、提现、普通私密转账 | 不因本规则增加 swap 手续费；不得通过这些入口实现绕过收费的兑换 |
| 多跳兑换（未来） | 对一个已授权用户订单的输入总额收取一次；独立 swap 订单各自收费 |

当前版本将 50 bps 作为强制规则，不提供任意降为零的报价参数或管理员豁免。未来若修改费率，需要明确的协议版本变更及治理流程。

### 6.5 平台运营金库与原子入账

平台运营金库独立于保管用户本金和包装资产储备的 `GoPayVault`。可采用专用 shielded 收款身份或兼容的金库合约，具体形式在实现时验证。仅收款并不会授权平台消费用户其他资产。

- 每笔 swap 的费用输出必须绑定当前金库配置，不能由用户、做市商或中继替换。
- 用户资金交换、费用输出和订单成交标记必须在同一业务原子边界完成；费用入账失败则不能单独完成兑换，兑换失败也不能单独收取平台费。
- 金库按资产 ID 分别持有费用，不默认自动兑换为 USDC。费用对应的包装资产仍受其原有储备和兑付约束，不能把收到包装代币理解为可再次提走底层抵押储备。
- 金库支出用于 GoPay 运营，采用授权多签并记录用途；不得调用用户储备管理权限挪用用户本金。运营支出流水与 swap 明细分开管理。
- 金库收款密钥或地址更新需授权和延迟生效；报价绑定金库配置版本，过期配置下的交易应重新报价或按明确的版本规则拒绝。
- 手续费数量应通过受保护的输出传递，并在电路内验证。公开精确的单笔手续费可能反推出输入金额，因此不应写入公开的逐笔手续费表；也需检查金库余额变化是否形成同类泄露。

费用输出的构造、收据加密和恢复必须兼容金库资产管理方式。上线前验证平台可接收、恢复和支出费用，同时不公开用户单笔交易信息。

## 7. Circuit 接口与不变量

以下为接口规划，参数的公开/私密分配及具体类型在实现阶段确定。

| Circuit | 主要验证 |
|---|---|
| `deposit` | 指定资产实际入账、金额一致、存入上限、入账凭证未重放 |
| `transferPrivate` | Note 所有权、未花费、守恒、输出授权 |
| `settleSwap` | 双方授权、报价有效、库存有效、净到账下限、费用、订单未消费 |
| `spendTreasury`（或金库钱包授权支出） | 运营多签权限、仅消费平台资产、支出输出绑定；具体接口取决于金库实现 |
| `cancelOrder` | 撤单权限、与成交互斥 |
| `withdraw` | 有效 Note 消费、实际兑付、目标地址及金额绑定 |
| `registerAsset` | 管理权限、唯一资产身份、配置有效性 |
| `registerAdapter` | 治理权限、验证逻辑版本、支持的资产范围与启停规则 |
| `createShieldedAsset` | 发行授权、唯一资产绑定；已有原生资产只登记不重复发行 |
| `scheduleConfigUpdate` | 管理权限、允许变更的字段、延迟生效时间 |
| `applyConfigUpdate` | 变更已授权且已达到生效条件 |
| `pause` / `unpause` | 授权操作、明确的资产和操作范围 |

### 7.1 逐资产守恒

对转账和兑换，每一种资产分别满足：

```text
该资产所有输入金额
  = 该资产收款与找零输出金额 + 该资产费用输出金额
```

费用输出不能重复计入。不能将不同资产按价格折算后只检查一个总数。存入和提现则分别加入已验证的外部入账或兑付项。

### 7.2 金额与授权

- 所有金额使用最小单位整数，客户端使用 BigInt，禁止浮点结算。
- 对金额、费用和中间乘积执行范围检查，明确除法舍入方向。
- 用户确认的是扣除费用后的净到账数量。
- `settleSwap` 根据用户输入总额自行计算 50 bps 平台费，验证输入资产 ID、费用承担方、金库接收标识和配置版本；不能相信报价中自报的 `feeAmount`。
- 用户输入资产满足“输入总额 = 兑换本金 + 平台费”；钱包选币超出输入总额的部分作为找零，不能参与计费。结合做市商输入及输出继续执行完整的逐资产守恒校验。
- 报价及授权绑定所有相关输出，防止替换收款人。
- 找零属于原授权方，不能由撮合服务任意指定。
- Witness 返回值不可信，必须通过电路约束验证其来源和关系。

### 7.3 原子性与失败

Midnight 存在 guaranteed 与 fallible 部分。仅把操作放进同一个交易对象，不足以证明所有业务效果一起回滚。

实现必须确认：Note 消费、输出创建、订单标记与资金移动属于同一原子业务边界。测试失败路径时，不能出现用户付款完成而做市商付款失败，或订单标记已消费但资产没有交换。

跨链提现应单独设计异步状态机、唯一兑付请求和恢复策略。不能在外链可能已付款时简单“超时退回”内部余额，否则会产生双重兑付。

## 8. 防止间接泄露

### 8.1 币种与访问模式

将私密 `assetId` 用作公开 Map 的查询键可能泄露币种。若要隐藏币种，可对公开资产配置根进行私密成员证明，并绑定当前允许的配置版本。

配置根不能单独解决所有泄露：费用、Vault 余额变化、资产转移形式和不同电路入口仍可能暴露信息，需审查完整交易。

### 8.2 交易形状

采用有限且固定的输入输出槽位、统一结算入口以及受约束的填充槽位，可以减少结构泄露。填充输入输出不能绕过守恒或双花验证。

批量提交只能改善部分关联风险，不能在低交易量条件下保证匿名。

### 8.3 证明与私密数据可用性

优先在用户设备生成证明。双方分别处理自己的秘密，不把双方私钥和完整 Note 秘密交给撮合服务。

必须提供：

- 加密且可验证的 Note 收据；加密内容与链上输出承诺绑定。
- 钱包私密状态的备份、恢复和密钥派生方案。
- 构建 Merkle 路径所需数据的可靠获取方式。
- 服务不可用时的恢复路径和重试语义。

链上承诺不能恢复丢失的 Note 私密内容。交易确认与收据交付之间的失败也必须可恢复。

## 9. 为什么第一版不采用隐私 AMM

公开 AMM 的储备变化往往能暴露资产和兑换数量；隐藏订单参数不足以隐藏资金流。

全隐私 AMM 还需要处理隐藏储备、状态更新、LP 份额、报价可用性、并发和提现。它可以作为后续研究方向，但不应在 MVP 阶段与跨链资产、多个稳定币和复杂钱包能力一起实现。

不同法币稳定币存在汇率变化。USDC/JPYC 或 USDC/XSGD 不能因为都叫稳定币就固定按 1:1 兑换。

## 10. 治理与信任边界

- 管理权限采用多签与延迟生效；具体实现取决于所选工具链支持。
- 资产启停、存入额度、费用规则及金库配置都需要版本化；当前平台费率固定为 50 bps，不允许按用户或交易对豁免。
- 不允许管理员直接改写用户余额或花费用户 Note。
- 升级不能隐式替换已有债权的资产来源；迁移需明确授权和守恒。
- 按存入、兑换和提现分别暂停，避免无必要地阻断退出。
- 正常可兑付状态下应尽量保留退出路径；储备或桥失效时不能承诺无条件兑付。

| 依赖方 | 主要信任或可用性风险 |
|---|---|
| 稳定币发行方 | 资产冻结、赎回和储备风险 |
| 桥或托管方 | 虚假入账、重复兑付、储备损失、停机 |
| 做市商 | 拒绝报价、价格不佳、库存竞争；不得因此获得单边扣款能力 |
| 报价服务 | 请求信息泄露、选择性转发 |
| 远程证明服务 | 私密输入泄露、服务不可用 |
| 治理 | 恶意升级或配置变更 |

## 11. 测试与验收

| 场景 | 预期结果 |
|---|---|
| 重复消费同一 Note | 仅第一次合法消费可成功 |
| 替换 Note 内容或 Merkle 叶子 | 验证失败 |
| 同一报价重放、跨网络重放 | 验证失败 |
| 替换收款人、找零或手续费输出 | 验证失败 |
| 做市商库存已被消费 | 本次兑换不产生单边付款 |
| 成交与撤单并发 | 只能成功一个 |
| 过期报价、过期配置授权 | 按规则拒绝 |
| 极大金额、溢出、舍入边界 | 不创造资产或突破费用上限 |
| 所有交易对、直接调用及替代结算入口 | 成功 swap 均收取按输入总额计算的 50 bps 平台费 |
| 输入 1,000 USDC | 平台收到 5 USDC，995 USDC 参与兑换，输出侧不重复扣费 |
| 最小单位、小额交易与超额选币找零 | 按规定向上取整；零本金或零净到账拒绝；找零不计费 |
| 伪造零费用、错误费用币种或金库收款方 | 拒绝结算 |
| 费用输出失败、兑换失败或撤单 | 不单独扣平台费或留下单边成交 |
| 金库越权支出或访问用户储备 | 拒绝操作 |
| 单笔费用及金库变化的隐私分析 | 不通过公开费用数值反推用户交易金额 |
| 重复跨链入账凭证 | 不重复创建余额 |
| 外链重组或未达最终性 | 不提前确认可花费的真实资产入账 |
| Fallible 部分失败 | 不留下单边扣款或错误成交状态 |
| 收据服务中断 | 用户可恢复已确认的输出信息 |
| 公开交易数据分析 | 不出现超出隐私声明的明文或访问泄露 |
| 新增兼容测试资产 | 不修改或重新部署兑换核心即可完成存取与兑换 |
| 错误适配器或 A 资产证明用于 B 资产 | 拒绝发行 |
| 相同存款跨发行实例重放 | 不重复铸造 |
| 未授权发行、篡改资产与 shielded 标识绑定 | 拒绝操作 |
| 资产停用后使用旧配置根或旧版本 | 不绕过当前操作限制 |
| 转账扣税或余额自动变化的资产 | 专用规则正确执行，或明确拒绝接入 |

测试应覆盖正常交易、恶意输入、并发和故障恢复。单纯编译通过不能证明隐私与资产安全。

## 12. 实施路线

### 阶段一：能力验证

- 固定 Midnight 网络、编译器、SDK 和钱包版本。
- 验证 shielded 资产的接收、消费、输出恢复及索引器数据可用性。
- 验证双方独立授权、证明组合、签名验证和交易平衡。
- 实测 guaranteed/fallible 失败行为。
- 确定采用原生 shielded 资产还是 Vault 内部 Note，记录资产转换边界。
- 验证 Factory 多资产发行或模板部署方案、资产标识绑定及适配器扩展方式。

### 阶段二：测试资产 MVP

- 使用 USDC、JPYC、XSGD 的明确标注测试资产。
- 实现私密转账、RFQ 整单兑换、撤单、存取。
- 实现固定 0.5% 平台手续费、独立运营金库收款与授权支出，并测试计费、舍入、原子入账及隐私。
- 做市商预先存入库存。
- 完成加密收据、备份恢复和公开数据隐私验证。
- 完成注册表与发行模块；新增第四种兼容测试资产，验证只调整注册配置和链下展示，无需修改兑换核心。

### 阶段三：真实资产接入

- 选择并验证实际发行方、桥或托管接入路径。
- 明确每种资产的兑付责任、额度和故障处理。
- 完成储备绑定、重放防护及跨链异步提现验证。
- 在独立安全审计和受限额度运行后逐步扩大范围。

### 阶段四：扩展

- 在 USDC、JPYC、XSGD 基础上，逐步接入经验证的 USDT、EURC、EURCV、tGBP、ZCHF、JPYSC、BRLA、AUDD、cNGN，覆盖第 3.1 节的全部稳定币范围。
- 加密资产仅接入 BTC、ETH；NIGHT 按单独的原生资产存取方案验证。
- 对兼容资产复用适配器；新链先验证新适配器，再启用资产。
- 引入更多做市商和报价比较。
- 评估批量结算、部分成交和隐私 AMM。

## 14. 尚需确定的产品与工程决策

1. 第一批真实资产的来源链、具体代币地址及发行版本。
2. 桥、发行方直发或托管凭证的接入方式。
3. 是否必须对公众隐藏交易币种，还是先保证数量和身份关联的隐私。
4. 钱包、证明运行位置和双方交易组合方案。
5. 平台金库的具体收款实现、运营多签成员和支出流程；计费规则已确定为用户承担输入总额的 0.5%，以输入资产支付。
6. 治理成员、升级延迟、紧急暂停和退出规则。
7. Factory 采用多资产合约还是每资产模板部署，以及适配器批准和版本迁移规则。

这些决策不影响测试资产原型，但决定生产部署的信任模型和隐私承诺。
